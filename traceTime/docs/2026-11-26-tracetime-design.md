# traceTime 桌面计时小组件 设计文档

- 日期：2026-11-26
- 状态：草案 v0.1（待评审，未提交）
- 范围：需求细化、核心概念定义、技术选型、系统架构与数据模型；不含实现计划

## 1. 背景与目标

用户在日常做事时，希望记录**完成一个任务真实花费的时间**以及**这段时间的使用轨迹**（何时开始、何时暂停、何时继续、何时完成），并在接近预计时间的关键节点得到**显著的渐进提醒**，促使自己尽快收尾。

核心价值排序：

1. **时间轨迹是第一优先级**：数据要完整、可信、不可被静默改写。
2. **提醒要足够显著但不骚扰**：颜色、字号、短时放大动画等方式渐进升级。
3. **操作要轻**：悬浮小组件 + 手动开始/停止，不打断工作流。

## 2. 核心概念

| 概念 | 定义 |
|------|------|
| 任务 Task | 一次有明确完成动作的事情，具有名称、预计时长、状态 |
| 工作段 Segment | 任务的一次连续工作时间，`开始时间 → 暂停/结束时间`，只增不改 |
| 事件 Event | 轨迹的最小单位：创建、开始、暂停、继续、完成、放弃、提醒触发、修改预计时间等 |
| 净耗时 | 所有工作段时长之和（不含暂停时间） |
| 墙钟耗时 | 任务开始到结束的真实世界时间跨度 |
| 预计时长 | 创建任务时设定的目标完成时间 |
| 渐进提醒 | 按净耗时占预计时长的百分比，分档触发的视觉/声音/系统通知 |

**轨迹的准确定义**：任务从创建到终止的完整事件序列 + 每个工作段的精确起止时间。轨迹数据只追加、不覆盖（编辑操作本身也作为事件记录）。

## 3. 需求细化

### 3.1 功能需求

**任务生命周期（全部手动触发）**

- 创建任务：输入名称 + 预计时长（预设档位 15m / 25m / 45m / 1h / 2h，可自由输入）+ 可选标签（预设：科研 / 行政 / 杂务，可在设置中增删；默认取上次使用的标签）
- 开始：创建后立即开始，或从待开始状态开始
- 暂停 / 继续：暂停期间的墙钟时间不计入净耗时，但轨迹中如实记录暂停事件
- 暂停原因：暂停时单点选择快捷标签：`临时离开`（洗手间/喝水等）/ `被干扰`（电话/消息/人）/ `切换任务` / `其他`；可跳过，默认记 `其他`
- 打断切换：选择 `切换任务` 后新建任务，新任务自动携带 `interruption_of = 原任务` 关联；原任务保持暂停，待新任务完成后由用户手动继续
- 长暂停质询：暂停超过阈值（默认 2 小时，可配置）后，用户下次打开或点击小组件时弹出轻提示：`任务 X 已暂停 N 小时——继续 / 完成 / 放弃`，避免任务长期挂起、工作段横跨多日污染时段分析；短暂停不受影响
- 完成：手动点击"完成"，任务结束；若已超时，超时部分被如实记录
- 放弃：手动终止，任务标记为"放弃"，轨迹保留

**记录与轨迹**

- 每个任务保存：完整事件序列、工作段列表、净耗时、墙钟耗时、预计时长、偏差（净耗时 − 预计时长）
- 暂停/继续次数、每次暂停的时长可查看
- 历史任务列表：按日期分组，展示名称、净耗时、预计时长、偏差、超时标记
- 单任务详情：时间轴视图（工作段与暂停段的横向条状图）

**渐进提醒**

按净耗时占预计时长的比例分档，每档触发一次（不重复触发）：

| 节点 | 触发条件（占预计时长） | 视觉表现 | 其他 |
|------|----------------------|----------|------|
| 提前预警 | ≥ 75% | 字体变琥珀色 | 可选轻提示音（默认关） |
| 临近期限 | ≥ 90% | 字体变橙色 + 字号轻微放大 + 组件边框变橙 | 可选提示音 |
| 到达期限 | ≥ 100% | 字体变红色 + 组件短时（约 3 秒）放大脉冲 + 常驻红框 | 系统通知（默认开） |
| 超时计时 | > 100% | 红色 + 显示"+超时 xx:xx"倒计改为正计时 | 每 10 分钟重复一次系统通知，可一键静音本任务 |

- 所有分档可在设置中全局调整百分比与开关
- 视觉动画持续数秒后回落到常态，但颜色状态保持
- 超时后任务不会自动结束，由用户手动完成/放弃

**界面（悬浮小组件）**

- 置顶悬浮小窗，可拖动位置，位置记忆
- 窗口行为（不影响其他程序）：
  - 不抢焦点：点击小组件不激活自身、不中断当前正在输入的程序（macOS non-activating panel / Windows WS_EX_NOACTIVATE）
  - 不进任务栏 / Dock、不占 Alt-Tab，仅通过托盘或全局快捷键呼出
  - 闲置淡化：无操作约 10 秒后整体透明度降至约 20%，鼠标悬停恢复，减少对其他程序视觉上的干扰
- 背景：默认毛玻璃（深色底 + 约 75–85% 不透明度 + 背景模糊），跨平台策略——macOS 原生 vibrancy；Windows 亚克力/Mica；Linux 检测不到模糊支持时降级为半透明纯色。设置中提供三档：`毛玻璃（默认）` / `半透明纯色` / `不透明`
- 全透明不采用：文字叠在任意内容上可读性不可控
- 常态尺寸约 260×120，超时脉冲时短时放大（约 ×1.15）后回落
- 三个区域：任务名（可截断）、主计时（大号等宽字体）、进度环 + 剩余/超时时间
- 操作按钮：暂停/继续、完成、放弃（放弃需二次确认）
- 空闲状态显示"开始新任务"入口

### 3.2 非功能需求

- 计时基于真实时间戳（墙钟），不依赖 tick 累加，保证睡眠唤醒、重启后计时准确
- 应用意外退出后重启：运行中的任务自动恢复，缺失的中间时段按"暂停"处理并记录异常事件
- 本地存储，无需联网；单文件 SQLite
- 冷启动 < 1 秒，内存占用低（小组件常驻）

### 3.3 分析能力预留（本期只记录原始数据，不做分析界面）

以下分析均从原始事件事后推导，不在记录时预计算。列出仅为验证数据模型是否够用：

- 任务被打断次数：统计任务 pause 事件中 `被干扰` + `切换任务` 的数量
- 时段可打断性：所有打断事件按发生时刻（小时）聚合
- 时段专注度：各时段工作段的连续时长分布（如平均连续工作段长度）
- 打断恢复：打断结束后原任务首个工作段的时长，近似衡量恢复成本
- 标签维度分析：各标签（科研/行政/杂务）的时长占比、被打断率对比
- 专注时段 × 标签：各时段各标签的平均连续工作段长度（如上午适合科研类长段工作）

原因标签由用户随手选择，存在主观误差，分析结论按趋势解读，不追求单次精确。

### 3.4 非目标（本期不做）

- 自动应用追踪 / 猜测任务内容
- 多任务并行计时
- 云同步、多设备
- 数据统计报表与导出（分析维度见 3.3，本期不实现界面）

## 4. 技术选型

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **Tauri 2 + Web 前端** | 包体小（~5MB）、内存低、Rust 后端稳定、原生通知/托盘/置顶均有官方插件、三平台覆盖好 | 需要少量 Rust 代码 | **采用** |
| Electron + Web | 生态最成熟 | 包体 ~100MB、内存高，与"常驻小组件"目标冲突 | 不采用 |
| 各平台原生（Swift/Kotlin/…） | 最佳原生体验 | 三平台三套代码，成本过高 | 不采用 |

前端框架：**Svelte 5**（轻量、编译产物小，适合小组件常驻场景；React 亦可，不构成架构差异）。
本地存储：**SQLite**（rusqlite），文件位于各平台标准应用数据目录。
通知：tauri-plugin-notification；声音：前端 Web Audio 播放短音效（跨平台一致）。
窗口能力：置顶、不抢焦点、无任务栏图标均走 Tauri 窗口配置 + 各平台少量原生适配；毛玻璃背景按平台降级策略实现（见 3.1）。

## 5. 系统架构

```
┌──────────────────────────────────────────┐
│  悬浮小组件窗口 (WebView, always-on-top)  │
│  ┌────────────────────────────────────┐  │
│  │  UI 层 (Svelte)                     │  │
│  │  - WidgetView（计时显示/动画）       │  │
│  │  - TaskForm（创建任务）              │  │
│  │  - HistoryView（历史/详情）          │  │
│  │  - SettingsView（提醒配置）          │  │
│  └──────────────┬─────────────────────┘  │
│                 │ Tauri IPC (invoke)      │
│  ┌──────────────▼─────────────────────┐  │
│  │  Rust 核心层                        │  │
│  │  - TimerService   计时状态机         │  │
│  │  - TaskService    任务/段/事件 CRUD  │  │
│  │  - ReminderEngine 分档判断与触发     │  │
│  │  - Store          SQLite 读写       │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
        │ 系统通知          │ SQLite 文件
```

**职责边界**

- Rust 层拥有计时状态机与所有数据写入，是唯一事实来源；前端仅展示与发起动作。
- 提醒的"分档判断"在 Rust 层（每秒 tick 检查），"视觉动画"在前端（Rust 发出事件，前端播放）。
- UI 独立模块：WidgetView 常驻；History/Settings 按需打开独立窗口，不挤占小组件空间。

## 6. 数据模型（SQLite）

```sql
-- 任务
CREATE TABLE tasks (
  id            TEXT PRIMARY KEY,        -- uuid
  name          TEXT NOT NULL,
  est_seconds   INTEGER NOT NULL,        -- 预计时长
  status        TEXT NOT NULL,           -- pending | running | paused | done | abandoned
  created_at    TEXT NOT NULL,           -- ISO8601 UTC
  finished_at   TEXT,
  net_seconds   INTEGER,                 -- 完成后固化
  gross_seconds INTEGER,                  -- 完成后固化
  parent_task_id TEXT REFERENCES tasks(id) -- 打断来源任务；因打断其他任务而创建时填写，可空
  tag           TEXT                     -- 任务标签（科研/行政/杂务…），可空
);

-- 工作段（轨迹的时段维度，只增不改）
CREATE TABLE segments (
  id        INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id   TEXT NOT NULL REFERENCES tasks(id),
  started_at  TEXT NOT NULL,
  ended_at    TEXT,          -- NULL 表示进行中的开放段
  kind      TEXT NOT NULL DEFAULT 'work' -- work | pause | anomaly
);

-- 事件（轨迹的事件维度，只增不改）
CREATE TABLE events (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id    TEXT NOT NULL REFERENCES tasks(id),
  at         TEXT NOT NULL,
  kind       TEXT NOT NULL,
  detail     TEXT          -- JSON：暂停事件如 {reason:"disturbance"}；修改预计如 {from:90,to:120}
);
-- kind 枚举: created | started | paused | resumed | finished | abandoned
--          | est_changed | reminder_fired | anomaly_recovered
-- paused 事件的 detail.reason 枚举: rest | disturbance | switch | other
CREATE INDEX idx_events_task_time ON events(task_id, at);
CREATE INDEX idx_segments_task ON segments(task_id, started_at);

-- 提醒触发记录（防重复触发）
CREATE TABLE reminder_fired (
  task_id  TEXT NOT NULL REFERENCES tasks(id),
  node     TEXT NOT NULL,                -- p75 | p90 | p100 | overdue_10m, ...
  fired_at TEXT NOT NULL,
  PRIMARY KEY (task_id, node)
);

-- 设置（KV）
CREATE TABLE settings (
  key   TEXT PRIMARY KEY,
  value TEXT NOT NULL
);
```

**设计要点**

- `segments` 与 `events` 冗余但互补：段用于精确计算与时间轴可视化，事件用于完整轨迹审计。
- 修改预计时间只产生 `est_changed` 事件并更新 `est_seconds`，原值保留在事件 detail 中，轨迹不被抹去。
- 所有时间戳使用 UTC ISO8601，展示时转本地时区。
- 原始事件保持原子、带类型、只追加；所有分析（3.3）在查询层推导，不在记录时预计算。

## 7. 计时状态机

```
            创建
  [pending] ──→ [running] ⇄ 暂停/继续 [paused]
                   │  │                │
                完成│  └──放弃(需确认)──┼──→ 放弃 [abandoned]
                   ▼                  │完成
              [done] ←────────────────┘
```

- 计时实现：进入 running 时记录 `segment.started_at = now()`；暂停/完成时写入 `ended_at`。净耗时 = Σ(段时长)，任何时刻由查询得出，不做内存累加。
- tick（1 秒）只负责刷新 UI 与提醒检查，不参与计时长度的计算。
- 超时后状态仍为 running（或 paused），只是显示层切换为"超时正计时"。

**异常恢复**：启动时发现状态为 running/paused 的任务——
- paused：原样恢复，无损失。
- running：关闭时刻未知，将缺失区间记为一条 `anomaly` 段 + `anomaly_recovered` 事件，任务转为 paused，等用户手动继续。宁可多记暂停，不伪造工作时间。

## 8. 提醒机制

ReminderEngine 在每次 tick 中执行：

1. 计算 `ratio = net_seconds / est_seconds`
2. 对照配置表（默认 75% / 90% / 100% / 超时每 10 分钟），查 `reminder_fired` 是否已触发
3. 未触发则写入记录，并通过 Tauri event 发送 `reminder` 事件到前端
4. 前端按节点等级播放对应动画（颜色过渡 + CSS transform 放大约 3 秒后回落）并可调用系统通知

节流与静音：

- 每个节点对每个任务只触发一次（超时节点按周期）
- 任务级静音：超时通知可被用户一键静默（不再系统通知，视觉保留）

## 10. 错误处理与边界

| 场景 | 处理 |
|------|------|
| 系统睡眠 | 计时基于时间戳自动正确；睡眠段会自然落入段内，净耗时含睡眠——视为"挂着没管"，符合"真实花费时间"语义，不特殊扣除 |
| 时钟回拨/修改 | 若检测到 `ended_at < started_at`，该段按 0 计并记 `anomaly` 事件 |
| 删除任务 | 仅软删除（hidden 标记），轨迹保留 |
| 名称过长 | 截断显示，数据保留全名 |
| 预计时长修改发生在已超时后 | 允许；重置该任务的 reminder_fired（记 est_changed 事件）——表示用户主动给了新期限 |

## 11. 测试策略

- **Rust 单元测试**：状态机流转、净耗时计算（含暂停/异常段）、ReminderEngine 分档与去重、时钟异常处理
- **集成测试**：SQLite 读写、启动恢复流程（模拟意外退出的 running 任务）
- **前端手动验收清单**：三档提醒动画表现、暂停/继续、超时正计时、历史时间轴渲染
- **MacOS平台冒烟**：置顶、通知、托盘、拖动记忆

## 12. 里程碑建议

1. **M1 可用核心**：创建/开始/暂停/完成 + 暂停原因快捷标签 + 任务标签 + SQLite 持久化 + 基础小组件 UI（置顶、不抢焦点）
2. **M2 轨迹完整**：事件/段记录、打断关联（interruption_of）、长暂停质询、历史列表、任务详情时间轴
3. **M3 提醒系统**：四档渐进提醒 + 系统通知 + 设置页
4. **M4 打磨**：异常恢复、闲置淡化与毛玻璃降级、位置记忆、超时静音
5. **M5 打磨**：三平台冒烟
